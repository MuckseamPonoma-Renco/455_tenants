# NYC311 reliability repair — September 14, 2026

## Verified causes

- Context handling downgraded an explicit south-elevator outage to a generic
  update, making the afternoon recurrence ineligible for filing. A prior morning
  outage had its own receipt and a subsequent restoration report.
- Closed DOB portal pages omit `SR Status`. The tracker retained earlier
  `In Progress` labels even when it had obtained a closure date.
- The portal fallback repeatedly selected the newest 25 cases, indefinitely
  excluding older cases. Failed/empty responses could falsely refresh check times.
- Failures after final submission could be retried without first reconciling a
  receipt. Additional evidence arriving during review could instead permanently
  skip an otherwise eligible filing.
- An unrelated watchdog validation error treated an unperformed physical lobby
  inspection as an overdue machine check, causing unnecessary repeated refreshes.

## Changes and safeguards

Explicit outage classification now wins over contextual update handling. A
narrow, same-chat reduced-service fragment is actionable, while mechanic presence
alone is not. Two exact source-guarded decisions and their existing incident were
corrected from a private backup; original messages, model evidence and downstream
receipts were preserved. A second application was a no-op.

The tracker verifies request identity, handles closed pages, rotates older checks,
separates attempts from verified freshness, reports failures, and commits per case.
Submission fencing, receipt-first persistence, current-payload revalidation and
same-incident receipt guards prevent blind retries and duplicate submissions.

The runtime received scoped patches, preserving its existing watchdog/WhatsApp
repairs and the original dirty checkout. Private database/source backups and
browser artifacts are not part of this repository. No synthetic complaint is used
as a production test; any normal filing must concern a real eligible incident.

Tests include classification, closed-page parsing, starvation prevention, failed
lookups, submission uncertainty, changed payloads, receipt conflicts, API callback
guards, operator visibility, exact repair backups/idempotence, and manual evidence
timestamps. Operational completion is established by actual receipts and live
readback, not this document or a green process heartbeat.
